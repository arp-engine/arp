13 脚本 Contract Complete

ArpScript 是 arp 引擎内置的、带类型标注的脚本语言。它把玩法规则、资源编排和工具逻辑放在可热替换的源码模块中，同时通过反射和模块注册受控地访问 C++ 宿主。

边界先说清楚：ScriptVM 负责解析、类型检查、编译和执行；它不负责窗口、渲染或资源所有权。脚本需要通过宿主模块调用引擎服务，宿主也必须明确检查参数和错误。

1. 一条完整的执行链路

公开 API 有意拆成几个阶段，便于编辑器做增量诊断，也便于服务器或工具在执行前拒绝不安全脚本：

  1. ScriptFrontend 完成 parse 与 semantic analysis；
  2. ScriptLowerer 生成并验证 canonical Typed IR；
  3. InterpreterBytecodeLowerer 将同一份 IR 确定性降为版本化 Program；
  4. runFunctionByName() 或 Vm 执行已验证 bytecode，结果和诊断放在 EvalResult 中。
源码 (.arp)
    │
    ▼
ScriptFrontend ──> ScriptLowerer ──> validated Typed IR
                                            │
                                            ▼
                              InterpreterBytecodeLowerer
                                            │
                                            ▼
                                  validated Program ──> Vm

2. 最小 ArpScript 程序

变量、参数和返回值使用类型标注。缩进表示代码块，函数和控制流的语法接近 Python，但类型检查和运行时值都由 ScriptVM 管理。

def score(base: int, bonus: int) -> int:
    var total: int = base + bonus
    if total > 100:
        return 100
    return total

def main() -> int:
    return score(72, 18)

宿主侧执行这段源码的最小流程如下。依赖图和 reflection registry hash 必须由宿主的版本化模块契约提供，禁止使用空值或文件名推断。

#include "scriptvm/interpreter/pipeline.h"
#include "scriptvm/interpreter/eval.h"

using namespace arp::scriptvm;

ScriptInterpreterBuildRequest request;
request.source = std::move(source);
request.filename = "score.arp";
request.moduleId = "tutorial.score";
request.moduleVersion = 1;
request.dependencyGraphHash = dependencyHash;
request.reflectionRegistryHash = reflectionHash;

auto built = ScriptInterpreterPipeline::build(request);
if (!built.ok()) {
    report(built.error);
    return;
}

arp::core::pmr::Vector<Value> args {
    &arp::core::defaultCpuMemoryResource()
};
auto result = runFunctionByName(built.program, "main", args);
if (!result.ok()) {
    report(result.error);
    return;
}

int value = 0;
if (!tryGetInt(result.value, value)) {
    report("main() did not return int");
}

3. 语言能力：函数、容器与闭包

当前语法覆盖标量、列表、字典、索引、lambda、条件、while、for ... in range()、异常处理和可变参数。闭包捕获的局部变量会由编译器提升到共享的 ScriptCell，因此下面的计数器会跨调用保留状态：

def make_counter(start: int) -> () -> int:
    var count: int = start
    def next() -> int:
        count = count + 1
        return count
    return next

def main() -> int:
    var counter: () -> int = make_counter(40)
    counter()
    return counter()       # 42

脚本类使用 class 声明字段和方法；导入的 C++ 类则走反射绑定（见第 7 章）。不要把脚本对象当作跨线程共享的普通 C++ 对象，VM、闭包和容器的生命周期应由拥有它们的运行时线程管理。

4. yield、生成器与 await

yield 会把当前值作为 Suspended 结果返回，适合把大批量工作拆成多次更新；await 消费宿主提供的 ScriptAwaitable。当 awaitable 尚未完成时，宿主等待自己的异步系统，再调用同一个 Vm 的 resume()。

def ticks(limit: int) -> int:
    var i: int = 0
    while i < limit:
        yield i
        i = i + 1
    return i

# C++ 侧：
auto first = vm.runFunctionByName(program, "ticks", args, &err);
if (err.code == ScriptDiagnosticCode::Suspended) {
    consumeYieldedValue(first);
}

// Await 挂起时：
auto pending = vm.run(program, &err);
if (err.code == ScriptDiagnosticCode::Suspended && vm.suspended()) {
    dispatchAsyncWork();
    auto completed = vm.resume(program, &err);
}

Suspended 不是失败。真正的失败仍会携带 ScriptDiagnosticCode、消息和 traceback；宿主必须分别处理这两类状态。

5. 模块：把宿主能力做成窄接口

脚本通过 import math 或 from math import double 获取模块导出。模块注册表先查源码解析器，再查显式的 v2 C++ plugin；已加载的源码模块会被缓存，并检测循环导入。

from math import double

def main() -> int:
    return double(21)

宿主模块只导出脚本真正需要的能力。例如，测试里的 math 模块导出了 double 和 abs：

ScriptPluginRegistrar registrar("math");
registrar.exportFunction("double",
    [](const arp::core::pmr::Vector<Value>& args) -> Value {
        int value = 0;
        if (args.empty() || !tryGetInt(args[0], value))
            return makeInt(0);
        return makeInt(value * 2);
    });

ModuleRegistry modules;
modules.installPluginModule("math", registrar.build());

Vm vm;
vm.setModuleRegistry(&modules);
auto result = vm.runFunctionByName(program, "main", args, &err);

标量、函数和反射类型都可以导出。bindType<T>() 只绑定已经登记到 reflection 数据库的 C++ 类型；构造函数、静态成员和方法是否可见，取决于该类型的反射契约。

6. 源码模块与 C++ 插件

需要从磁盘加载 .arp 时，给 ModuleRegistry 设置 SourceResolver。解析器负责读取文件、执行本章第 2 节的 parse → analyze → compile 流程，并返回一个 ModuleExports；注册表会负责缓存和循环检测。

modules.setSourceResolver([&compiler](const core::pmr::String& name) {
    auto source = compiler.readModule(name);       // 应限制在脚本根目录内
    if (!source)
        return std::shared_ptr<ModuleExports> {};
    return compiler.compileExports(*source, name);
});

需要原生扩展时使用显式 .arpplugin manifest 和 CppPluginImporter，不要让脚本直接拼接 DLL 路径。插件的模块名、源码、入口和缓存目录都由 importer 校验，模块值还会持有 native lifetime，避免反射函数悬空。

7. 诊断、资源和线程纪律

  • 解析、语义、编译阶段统一读取 ScriptDiagnostic 的 code/message/line/column，在编辑器中标到原始源码行；
  • 执行阶段检查 EvalResult::ok()，并把 VmError::traceback 和宿主诊断一起写入日志；
  • 模块解析器必须限制根目录、拒绝路径穿越，并限制脚本可见的宿主函数集合；
  • 脚本值使用 arp 的 core::pmr 分配器，宿主构造参数向量时也应使用 defaultCpuMemoryResource()；
  • 一个 Vm 的挂起帧、闭包和临时容器不要跨线程迁移；需要并发时，为每个执行线程建立独立 VM 和明确的消息接口。

实践顺序：先让脚本只返回纯值，再接入一个窄的 host module，最后才开放资源、网络或异步能力。每新增一个导出，都应同时增加参数错误、模块缺失和 traceback 的测试。

8. 验证路径
