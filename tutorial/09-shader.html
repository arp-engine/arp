09 Shader Prototype Complete

arp 以 Slang 作为 shader 权威源码，离线生成 SPIR-V、MSL、WGSL 与 YAML reflection。本文介绍 shader 工件链路，以及 C++ row-major 矩阵存储与 Slang 矩阵 ABI 的硬约束。具体 shader/backend 能力和验证状态以 RHI 能力矩阵为准。

1. Shader：Slang 统一着色语言与多后端编译

shader 编译器与工件 contract 位于 src/shader。普通目标包括 SPIR-V / MSL / WGSL；WebGL1 另有 Slang 派生 GLSL ES 1.00 工件，只能在显式 opt-in 的 WebGL Prototype 工具链中使用，不意味着共享生产 shader/backend 能力。

1.1 后端无关的统一编译 API

src/shader/shader_compiler.h 暴露了与 RHI 同源的「上层只声明、后端内部分支」契约。ShaderCompiler::compile() 接受一份请求、返回字节码 + 反射数据，全程不暴露任何原生 API：

枚举 / 结构含义
ShaderStageVertex / Fragment / Compute 三个阶段
TargetBackendSpirV / Msl / Wgsl 三个通用离线目标
BindingTypeUniformBuffer / StorageBuffer / SampledTexture / StorageTexture / Sampler
VertexAttributeFormatFloat2 / Float3 / Float4（顶点属性位宽）
ShaderCompileRequestsourcePath / sourceCode / moduleName / target / entryPoints
ShaderCompileResultsuccess / diagnostics / bytecode / bindings / reflection
ShaderReflectionentryPoints / bindings / vertexAttributes / pushConstantSizeBytes
 
// 一次编译：从 Slang 源码到某一后端的字节码 + 反射
arp::shader::ShaderCompileRequest req;
req.sourceCode  = readFile("shaders/wocc/particles.slang");
req.moduleName  = "Particles";
req.target      = arp::shader::TargetBackend::SpirV;
req.entryPoints = {{"vertexMain", arp::shader::ShaderStage::Vertex},
                   {"fragmentMain", arp::shader::ShaderStage::Fragment}};

arp::shader::ShaderCompileResult res = arp::shader::ShaderCompiler{}.compile(req);
if (res.success) {
    uploadToGpu(res.bytecode);                       // 交 RHI 创建 ShaderModule
    validatePipelineAgainst(res.reflection);         // 见第 2 章校验
}

1.2 编译流水线：scripts/compile_shaders.py

项目 shader 工件由 Slang 离线构建生成；构建会调用 scripts/compile_shaders.py，并在具备依赖时用 SPIRV-Reflect 生成权威的 .reflection.yaml。直接执行工具时显式指定 Slang 编译器：

python scripts/compile_shaders.py --slangc "C:/VulkanSDK/1.4.350.0/Bin/slangc.exe"

# 完整引擎构建也会构建选定 preset 的 shader 工件
python scripts/build.py --preset win-vulkan-debug shaders

生成流程固定使用 -matrix-layout-row-major，并对 WGSL 执行受 contract/test 约束的目标适配；不支持的接口/语义必须给出诊断，不能通过猜测绑定或静默修补产出生产工件。

WGSL 适配包含按明确 metadata 处理绑定、entry-point IO 与 storage texture format/access。最终工件与 reflection contract 是运行时加载和 pipeline validation 的事实源。

  • set_wgsl_push_constant_binding()：依据 push-constant contract 生成 WGSL uniform binding。
  • set_wgsl_vertex_output_locations()：为顶点输出字段生成 location。
  • set_wgsl_storage_texture_format_and_access()：依据 metadata 设置 storage texture format/access。

反射 YAML 如何产生：离线流程读取生成的 SPIR-V 及 SPIRV-Reflect 输出，并与受版本控制的 shader/entry-point metadata 结合，生成 .reflection.yaml。运行时用 ShaderReflectionCache 加载 YAML；缺失、冲突或无法确定的 reflection 必须失败关闭。

1.3 反射缓存与 Pipeline 校验

编译产物不只是字节码。反射数据以 YAML 工件保存，运行时通过反射缓存和校验器，把「着色器实际签名」与「上层声明的管线布局」对齐：

类型职责
ShaderReflectionCache从 YAML 加载 ShaderReflectionModule（loadFromYaml / loadFromFile），校验版本化反射契约
ShaderPipelineReflectionValidatorvalidate(ShaderPipelineLayoutDesc, ShaderReflection) 校验 push-constant 尺寸、顶点属性与着色器反射一致，返回 ShaderPipelineValidationResult
 
// 校验：上层声明的管线布局必须匹配着色器真实反射
arp::shader::ShaderPipelineLayoutDesc layout;
layout.pushConstantSizeBytes = sizeof(PbrPushConstants);
layout.vertexAttributes      = { {"position","POSITION",Float3,0}, {"normal","NORMAL",Float3,1} };

auto mod = arp::shader::ShaderReflectionCache::loadFromFile("pbr_scene.reflection.yaml").module;
arp::shader::ShaderPipelineValidationResult v =
    arp::shader::ShaderPipelineReflectionValidator::validate(layout, mod.reflection);
assert(v.success);   // 不一致会在编译期/加载期被确定性捕获，而非 GPU 报错

1.4 当前 shader 工件

shader 模块由 CMake 和 Slang 工具链按 entry point 构建。以下是仓库当前维护的代表性工件：

模块源作用
粒子场景shaders/wocc/particles.slang粒子绘制 shader；C++ push-constant 镜像与生成反射由 shader contract test 核对
Queen 场景shaders/examples/build_a_queen.slangBuild a Queen 场景着色器；具体目标工件依所选构建 profile 而定
WebGL1 fixturetests/fixtures/webgl1_graphics.slang显式 opt-in Prototype 工具链的 GLSL ES 1.00 输入，不代表通用生产目标

要新增 shader，应把 Slang 源和明确 entry-point/资源 metadata 接入现有 CMake 与编译工具链，再生成目标字节码与 YAML reflection，并补足 shader contract tests。运行时通过反射与 pipeline contract 校验后才允许创建资源；不要把 WebGL1 专用 GLSL ES 100 工件误当作通用生产目标。

2. Shader ABI：CPU 结构体 ↔ GPU uniform/cbuffer

多目标编译仍要求 shader 声明的 buffer ABI 与 CPU 上传字节逐项一致：字段偏移、数组 stride、矩阵布局和 push-constant 尺寸都必须有反射或 contract-test 证据。不能仅凭“多后端同一份源码”推断各目标 ABI 自动一致。

2.1 为什么需要 ABI contract

  • 渲染时你常把一小块 CPU 内存（如每帧的 view-projection、材质参数）通过 push constant 或 uniform buffer 推给 GPU。
  • GPU 侧结构体布局（成员偏移、对齐、大小）由着色器源码定义；CPU 侧的 C++ 镜像结构体必须与之逐字节一致，否则 GPU 读到错位字段 → 画面错乱，或 RHI/校验器直接拒绝。
  • 共享 profile 使用同一 Slang 源和有版本的反射/lowering contract；WebGL1 是单独的 Prototype shader artifact/profile，不能据此推断四后端一致性。

2.2 CPU 与 shader buffer layout

buffer 的字段偏移、大小、数组 stride 和矩阵布局必须由 Slang 源、反射 metadata 与生成工件共同确定。不要把通用图形 API 的布局经验当作 arp ABI；以生成 reflection 和 contract test 为准。

工程结论：不要用通用对齐口诀推导实际偏移或 size。对每个目标，以生成 reflection、Slang 目标工件与 C++ 镜像的契约测试为准；差异必须由显式 ABI metadata 和测试解释。

2.3 实战：引擎内真实 push-constant 结构体的字节核算

粒子系统展示了为什么要把 CPU payload、Slang 字段和 reflection size 分别核对，而不能混为一个数字：

表示字段构成字节数依据
C++ ParticlePushConstantsfloat[16] + 六个 uint32、两个 float 与四个 float 的显式尾部空间sizeof = 112src/renderer/particles/particle_draw_plan.h
Slang reflection矩阵、六个 uint、两个 float 与一个 pad3 floatpushConstantSizeBytes = 100tests/contract/shader_tests.cpp 断言反射 size；使用时必须核对具体 target package/binding contract
TrailBeamPushConstantsfloat[16] + 两个 uint32 与两个 float80以 C++ 结构定义及对应 Slang/reflection contract 为准

Matrix Layout：C++ core::Mat4 使用 row-major 字节；Slang 保持默认 float4x4 声明，所有离线目标显式启用 -matrix-layout-row-major。不得在 shader 字段写 row_major 或 column_major 来猜测 native ABI。push-constant struct 内也不要放 // 注释，以免当前反射 size parser 将注释吸收进字段 token。

2.4 L2 push-constant 上限

arp 的 L2 contract 将单次 atomic push-constant payload 上限定义为 256 字节。这是跨后端的引擎契约，不是 Vulkan 设备固定上限；每个 backend/profile 仍需满足自己的 capability、reflection、payload 与预算 gate。

越界的真实后果：

  • 尺寸不得超过 L2 上限；创建管线、lowering 或录制阶段任何 gate 不满足都必须确定性失败。
  • 新增数据应按真实字段 ABI 设计；能否改用 uniform buffer 取决于目标 backend 的已验证 lowering，而不是静默替代。

失败关闭：帧计划阶段会拒绝 pushConstantSizeBytes > 256；具体 backend 还会校验 lowering 能力、管线容量和反射绑定，不允许通过占位或未声明模拟继续执行。

2.5 Push-constant 校验边界

布局和命令错误应尽早确定性拒绝，但每项校验覆盖的边界不同：

  • 防线一 · PipelineLayout 校验（创建管线前）。RHI（L2）在创建管线前校验 push-constant 布局：同一 shader stage 的 byte range 重叠 → 确定性失败；offset + size 回绕溢出 → 确定性失败。同时 ShaderPipelineReflectionValidator::validate(ShaderPipelineLayoutDesc, ShaderReflection) 用反射里的 pushConstantSizeBytes 校验你声明的尺寸与顶点属性是否和着色器真实签名一致。
  • 防线二 · 命令期 push-constant 校验（录制时）。Null 后端在 pass 内录制 pushConstants() 时校验：必须先绑管线再 push（pipeline-before-push）、shader stage 必须在管线声明范围内、更新非空且 range 覆盖完整、offset + size 不溢出；任一不满足则不在 pass 内录制任何命令——把后端专属规则挡在 L2 之下，给上层确定性失败而非原生 UB。

这些检查降低了已覆盖路径中的错配风险，不代表所有 shader/backend 自动一致。每个消费该 payload 的 target 仍需通过对应 reflection、lowering 和执行 contract。

2.6 动态 uniform 偏移对齐

若使用 uniform buffer 动态偏移，偏移必须满足目标 device/runtime 查询到的 uniformBufferOffsetAlignment。WebGPU profile 从浏览器设备 probe 读取该限制；缺失或非法时会失败关闭，不得硬编码为跨设备常量。

暂存上传和纹理行距也各有独立的 backend/API 对齐契约，按资源请求与 native limit 计算，不应从 uniform 对齐值推导。

两个不同层级的对齐：

  • 结构体 ABI（§2.2）——buffer 里「结构体的成员怎么排」，以反射和 contract test 为准。
  • 动态 uniform 偏移对齐（本节）——「绑定哪个 buffer 的哪个偏移」。

两者都要满足，但属于不同的约束来源。

2.7 设计 ABI-safe 结构体：清单

  1. 先从现有 shader、binding metadata、reflection 与 ABI contract 测试中确认目标布局，再定义 C++ 镜像。
  2. 跨语言矩阵统一使用 CPU row-major 字节、Slang 默认 float4x4，离线编译显式指定 -matrix-layout-row-major。
  3. push-constant payload 不超过 L2 256 字节上限，且还要通过目标 backend 的实际 capability 与 pipeline-capacity gate。
  4. 用生成 reflection 和 ShaderPipelineReflectionValidator 校验布局；有矩阵字段时同时测试 SPIR-V decoration、非对称矩阵数值及 reflection size。
  5. 共享源码不自动证明 backend ABI 等价；新增目标必须有 contract 覆盖，不支持或无法证明时确定性失败。

示例与验证边界

矩阵 layout 的具体断言位于 tests/shader_tests.cpp 与 shader contract tests：源码必须使用默认 float4x4，SPIR-V decoration 和非对称矩阵数值探针必须匹配，reflection push-constant size 必须与字段总和一致。单个示例编译成功不能替代这些契约测试，也不能证明所有 backend/platform 已验证。

快速上手清单

  1. 用 Slang 写一个 .slang 模块，声明 entry point、uniform/cbuffer 与 [[vk::push_constant]] 结构体。
  2. 按实际 Slang/resource metadata 与反射 contract 定义 C++ 镜像；矩阵遵守本章 Matrix Layout 规则，push constant 不超过 L2 256 字节上限。
  3. 将源、entry point 和明确资源 metadata 接入 scripts/compile_shaders.py / CMake 构建目标，生成支持的字节码与 YAML reflection。
  4. 运行时用 ShaderReflectionCache::loadFromFile() 读反射，用 ShaderPipelineReflectionValidator::validate() 校验与本次 CPU payload 对应的管线布局；不得默认 sizeof(CppStruct) 就等于目标 reflection size。
  5. 录制时用 pushConstants(stages, offset, sizeof(MyPush), &data) 推送；若尺寸/对齐不对，RHI 会在创建管线或录制期确定性报错。
