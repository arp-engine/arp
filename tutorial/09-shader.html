09 Shader Prototype Complete

渲染管线最终要落到 GPU 可执行的字节码。arp 引擎的着色器子系统（src/shader）与 RHI（见 01 渲染管线）共享同一条设计哲学：上层写一次，后端分支在底层完成——引擎以 Slang 作为统一着色语言，由同一套源码编译出 SPIR-V / Metal / WGSL 三个目标，分别喂给 Vulkan、Metal、WebGPU 后端。本文先讲清这套编译与反射链路，再专门拆解 arp 的统一内存对齐约定：为什么 CPU 侧结构体必须与 GPU 侧 uniform/cbuffer 逐字节一致，以及引擎如何用 std140 规则与两层校验把对齐错误挡在加载/录制期。

1. Shader：Slang 统一着色语言与多后端编译

渲染管线最终要落到 GPU 可执行的字节码。arp 引擎的着色器子系统（src/shader）与 RHI 共享同一条设计哲学：上层写一次，后端分支在底层完成。引擎以 Slang 作为统一着色语言，由同一套 .slang 源码编译出 SPIR-V / Metal / WGSL 三个目标，分别喂给 Vulkan、Metal、WebGPU 后端——上层开发者永远只面对 Slang 与反射元数据，不接触任何原生着色器方言。

1.1 后端无关的统一编译 API

src/shader/shader_compiler.h 暴露了与 RHI 同源的「上层只声明、后端内部分支」契约。ShaderCompiler::compile() 接受一份请求、返回字节码 + 反射数据，全程不暴露任何原生 API：

枚举 / 结构含义
ShaderStageVertex / Fragment / Compute 三个阶段
TargetBackendSpirV / Msl / Wgsl 三个编译目标
BindingTypeUniformBuffer / StorageBuffer / SampledTexture / StorageTexture / Sampler
VertexAttributeFormatFloat2 / Float3 / Float4（顶点属性位宽）
ShaderCompileRequestsourcePath / sourceCode / moduleName / target / entryPoints
ShaderCompileResultsuccess / diagnostics / bytecode / bindings / reflection
ShaderReflectionentryPoints / bindings / vertexAttributes / pushConstantSizeBytes
 
// 一次编译：从 Slang 源码到某一后端的字节码 + 反射
arp::shader::ShaderCompileRequest req;
req.sourceCode  = readFile("wocc/pbr_scene.slang");
req.moduleName  = "WoccPbrScene";
req.target      = arp::shader::TargetBackend::SpirV;
req.entryPoints = {{"vertexMain", arp::shader::ShaderStage::Vertex},
                   {"fragmentMain", arp::shader::ShaderStage::Fragment}};

arp::shader::ShaderCompileResult res = arp::shader::ShaderCompiler{}.compile(req);
if (res.success) {
    uploadToGpu(res.bytecode);                       // 交 RHI 创建 ShaderModule
    validatePipelineAgainst(res.reflection);         // 见第 2 章校验
}

1.2 编译流水线：scripts/compile-shaders.ps1

引擎的构建入口是 PowerShell 脚本 compile-shaders.ps1，它对每个着色器模块依次调用 Slang 编译器 slangc，并产出三份字节码与一份反射 JSON（落在 artifacts/direct/shaders）：

# 一套源码 → 三个后端目标（多 entry point）
slangc wocc/pbr_scene.slang `
  -target spirv  -profile spirv_1_5 -entry vertexMain -entry fragmentMain -o pbr_scene.spv
slangc wocc/pbr_scene.slang `
  -target metal  -profile sm_6_0    -entry vertexMain -entry fragmentMain -o pbr_scene.metal
slangc wocc/pbr_scene.slang `
  -target wgsl   -profile sm_6_0    -entry vertexMain -entry fragmentMain -o pbr_scene.wgsl

WGSL 目标额外经过三段脚本后处理，把 Slang 默认不显式的绑定信息补齐，使其符合 WebGPU 语义：

  • Set-WgslPushConstantBinding：为 push-constant uniform 注入 @binding(0) @group(0)。
  • Set-WgslVertexOutputLocations：给顶点输出结构体逐字段注入 @location(N)。
  • Set-WgslStorageTextureFormatAndAccess：修正 storage 纹理的 format/access（如 GI 的 rgba16float write）。

反射 JSON 怎么来的：脚本对源码做静态扫描——按 token 名识别绑定（如 SceneConstants 映射到 set=0,binding=0 的 UniformBuffer）、解析 [[vk::push_constant]] 结构体算出 push-constant 字节数、解析 VertexInput 结构体得到顶点属性与 location。该 JSON 是运行时 ShaderReflectionCache 的输入，不依赖运行时编译。

1.3 反射缓存与 Pipeline 校验

编译产物不只是字节码。反射数据被序列化为 JSON，运行时通过两个无状态的工具类消费，把「着色器实际签名」与「上层声明的管线布局」对齐：

类型职责
ShaderReflectionCache从 JSON 加载 ShaderReflectionModule（loadFromJson / loadFromFile），缓存模块名、源路径与三后端路径
ShaderPipelineReflectionValidatorvalidate(ShaderPipelineLayoutDesc, ShaderReflection) 校验 push-constant 尺寸、顶点属性与着色器反射一致，返回 ShaderPipelineValidationResult
 
// 校验：上层声明的管线布局必须匹配着色器真实反射
arp::shader::ShaderPipelineLayoutDesc layout;
layout.pushConstantSizeBytes = sizeof(PbrPushConstants);
layout.vertexAttributes      = { {"position","POSITION",Float3,0}, {"normal","NORMAL",Float3,1} };

auto mod = arp::shader::ShaderReflectionCache::loadFromFile("pbr_scene.reflection.json").module;
arp::shader::ShaderPipelineValidationResult v =
    arp::shader::ShaderPipelineReflectionValidator::validate(layout, mod.reflection);
assert(v.success);   // 不一致会在编译期/加载期被确定性捕获，而非 GPU 报错

1.4 参考实例：world_of_claudecraft 的着色器

本项目把三个 Slang 模块接入了编译脚本，正是渲染管线（01 节）与后处理（01 节 FXAA）的着色器落点：

模块源作用
WoccPbrSceneshaders/wocc/pbr_scene.slang前向 PBR 场景着色（BaseColor / Normal / MetallicRoughness / 蒙皮矩阵集）
WoccSkyshaders/wocc/sky.slang程序化天空盒，被 extract() 的 "wocc.sky" payload 驱动
WoccPostshaders/wocc/post.slang后处理链：Bloom 降采样/合成 + ACES tonemap + grade，对应 01 节的 recordGraphPostprocess()

要新增一个着色器：在 compile-shaders.ps1 注册源路径与模块名、列出入入口，运行脚本，产物即落到 artifacts/direct/shaders；运行时用 ShaderReflectionCache 读反射、用 ShaderPipelineReflectionValidator 对齐绑定布局，最后交给 RHI 创建 ShaderModule。整条链路与 RHI 的「后端中立」约束一致——你写的仍是 Slang，而不是 Vulkan GLSL、Metal Shading Language 或 WGSL 三种方言。

2. 统一内存对齐：CPU 结构体 ↔ GPU uniform/cbuffer

多后端编译解决了「一份源码、三套字节码」的问题，但还有一个更隐蔽的坑：同一份着色器里声明的 uniform/cbuffer 布局，必须和你在 CPU 侧喂进去的内存块逐字节一致。这就是 arp 的「统一内存对齐」——它不是一个独立模块，而是贯穿于 Slang 打包规则、C++ 镜像结构体、以及 RHI 校验的一道纪律。

2.1 为什么需要统一对齐

  • 渲染时你常把一小块 CPU 内存（如每帧的 view-projection、材质参数）通过 push constant 或 uniform buffer 推给 GPU。
  • GPU 侧结构体布局（成员偏移、对齐、大小）由着色器源码定义；CPU 侧的 C++ 镜像结构体必须与之逐字节一致，否则 GPU 读到错位字段 → 画面错乱，或 RHI/校验器直接拒绝。
  • arp 在三个后端用同一套 Slang 源码，因此「统一对齐」的含义是：一份代码定义的布局，在 Vulkan / Metal / WebGPU 三个后端都得到一致解释，CPU 侧只需维护一份镜像。

2.2 std140：arp 的统一内存对齐规则

Slang 把 cbuffer / uniform 与 [[vk::push_constant]] 结构体按 std140 规则打包：SPIR-V 反射出 std140 偏移；Metal（MSL）沿用其 float4 默认对齐；WGSL 经 slangc 后处理为每个字段注入 @align(16)。三套产物对同一结构体的解释一致。牢记以下规则：

类型对齐占用大小说明
float / int / uint44标量按自身大小对齐
vec2882 个分量
vec31612（占位 16）对齐到 16，后面不能直接贴一个 float 而不产生隐式 padding
vec41616最常用、最安全的基本粒度
mat4 (float4x4)1664按 4 个 vec4 列排布
数组 T[N]align(T) 向上取 16N × roundUp(sizeof(T), 16)每个元素 stride 对齐到 16
结构体max(成员对齐) 向上取 16roundUp(成员总和, 16)整体大小也要补到 16 的倍数

工程结论：始终把成员按「大块在前」排序，用 vec4 粒度打包参数；避免 vec3 后面紧跟 float 这类会产生隐式 padding 错位的写法。让结构体总大小是 16 的倍数。

2.3 实战：引擎内真实 push-constant 结构体的字节核算

引擎里三处真实的 push-constant 结构体，都是 std140 对齐的干净范例：

结构体（来源）字段构成字节数对齐证据
ParticlePushConstants
粒子 L2 契约		1 × float4x4 viewProjection64Vertex | Fragment；offset 0
TrailBeamPushConstants
trail/beam L2 契约		float4x4(64) + 4 × uint32（visualFamily / isTextured / trailWidth / beamLength）80Vertex | Fragment；offset 0，size 80
StylizedScenePushConstants
samples/stylized/stylized_scene_draw_plan.h		float4x4(64) + 12 × float[4]（共 192）256Slang 源 shaders/stylized/scene.slang 同构；编译出 WGSL 每个字段标 @align(16)，MSL 为连续 float4

以 StylizedScenePushConstants 为例，它的 CPU 镜像（C++）与 Slang 源逐字段对应，总大小正好是 256 字节 = 16 个 16 字节槽：

// samples/stylized/stylized_scene_draw_plan.h —— CPU 镜像
struct StylizedScenePushConstants {
    float viewProjection[16];        // 64B  (mat4, 占 4 个 16B 槽)
    float cameraPositionAndTime[4];  // 16B
    float baseColor[4];              // 16B
    float shadeColor[4];             // 16B
    float lightDirectionAndWrap[4];  // 16B
    float rampParams[4];             // 16B
    float fogParams[4];              // 16B
    float materialParams[4];         // 16B
    float pbrParams[4];              // 16B
    float pbrExtraParams[4];         // 16B
    float emissiveParams[4];         // 16B
    float stylizedParams[4];         // 16B
    float gltfExtensionParams[4];    // 16B
};  // sizeof == 256，且每个字段 16 字节对齐

同一结构体的 Slang 源码只声明语义字段，布局交给 slangc 按 std140 决定；编译产物（WGSL）显式为每个字段标注 @align(16)——这正是「统一内存对齐」在三个后端的落地：

// shaders/stylized/scene.slang —— 统一的着色器侧定义
struct StylizedScenePushConstants {
    row_major float4x4 viewProjection;
    float4 cameraPositionAndTime;
    float4 baseColor;
    float4 shadeColor;
    // ... 其余 9 个 float4 字段 ...
    float4 gltfExtensionParams;
};

2.4 256 字节 push-constant 预算的硬约束

Vulkan 的 push-constant 上限通常为 256 字节（maxPushConstantsSize）。arp 把场景着色器严格约束在 256 字节预算内。这条约束不是 Slang 报的，而是真实的工程教训：

越界的真实后果：

  • push-constant 涨到 288 字节 → Vulkan 提交时失败：vkQueueSubmit failed: -4。
  • 用一个 float4 载荷把尺寸抬到 272 字节 → 测试在 Vulkan submit 失败。
  • 结论：引擎契约要求 256 字节预算内打包（256-byte-budget packing）。新增字段要么复用现有 vec4 槽位，要么改用 uniform buffer 而非 push constant。

现在由 RHI 硬性强执：帧计划阶段的 validatePushConstants 会在 pushConstantSizeBytes > 256 时确定性抛错，不必再等到 Vulkan 提交期以 vkQueueSubmit failed: -4 失败。因此越界在录制前就会被捕获——把「288/272 字节」这类错误挡在加载/编译期，而非运行时 UB。

2.5 RHI 的两条对齐校验防线

对齐错误若在 GPU 运行期才暴露，调试成本极高。arp 把校验前移到确定性的两道防线：

  • 防线一 · PipelineLayout 校验（创建管线前）。RHI（L2）在创建管线前校验 push-constant 布局：同一 shader stage 的 byte range 重叠 → 确定性失败；offset + size 回绕溢出 → 确定性失败。同时 ShaderPipelineReflectionValidator::validate(ShaderPipelineLayoutDesc, ShaderReflection) 用反射里的 pushConstantSizeBytes 校验你声明的尺寸与顶点属性是否和着色器真实签名一致。
  • 防线二 · 命令期 push-constant 校验（录制时）。Null 后端在 pass 内录制 pushConstants() 时校验：必须先绑管线再 push（pipeline-before-push）、shader stage 必须在管线声明范围内、更新非空且 range 覆盖完整、offset + size 不溢出；任一不满足则不在 pass 内录制任何命令——把后端专属规则挡在 L2 之下，给上层确定性失败而非原生 UB。

这两条防线保证：对齐/尺寸错误在加载期或录制期就被确定性捕获，而不是 GPU 静默错位渲染。配合 ShaderPipelineReflectionValidator，push-constant 的尺寸与着色器反射永远保持同步。

2.6 动态 uniform 偏移对齐（256 字节）

若你用的是 uniform buffer（描述符绑定的 UBO，而非 push constant），并按帧用动态偏移绑定同一 buffer 的不同槽位，那么偏移量必须是 uniformBufferOffsetAlignment 的倍数——WebGPU 运行时档案里该值就是 256 字节（WebGpuRuntimeProfile::uniformBufferOffsetAlignment = 256）。

同一 256 字节粒度也出现在 RHI 的暂存上传池（staging upload pool）子分配对齐（alignmentBytes = 256），以及纹理上传的行距（row pitch 必须 256 字节对齐）。注意：

两个不同层级的对齐：

  • 结构体内部 std140 对齐（§2.2）——buffer 里「结构体的成员怎么排」。
  • 动态 uniform 偏移对齐（本节）——「绑定哪个 buffer 的哪个偏移」。

两者都要满足，但属于不同的约束来源。

2.7 编写对齐安全的结构体：清单

  1. 用 float4 / float4x4 粒度设计 push-constant / UBO 结构体。
  2. 把 mat4 放在最前；其余参数按 vec4 打包，必要时显式 padding 到 16 字节。
  3. 总大小取 16 的倍数；push-constant 总大小 ≤ 256 字节（Vulkan 预算）。
  4. C++ 镜像结构体与 Slang 结构体字段顺序、类型、大小一一对应；用 sizeof() 作为 pushConstantSizeBytes，并交给 ShaderPipelineReflectionValidator 校验。
  5. 跨后端一致性由 Slang 单一源码保证；不要为某个后端手写特化布局。

参考实例：world_of_claudecraft 的着色器用法

本项目的场景着色器（WoccPbrScene）通过 StylizedScenePushConstants 的 256 字节 push-constant 块接收每帧相机与材质参数；天空盒（WoccSky）与后处理（WoccPost）各自声明自己的 push-constant / 采样器绑定。新增着色器时，先按 §2.2–§2.7 设计好对齐安全的 C++ 镜像，再在 compile-shaders.ps1 注册模块，最后用 ShaderPipelineReflectionValidator 对齐反射。

快速上手清单

  1. 用 Slang 写一个 .slang 模块，声明 entry point、uniform/cbuffer 与 [[vk::push_constant]] 结构体。
  2. 按 §2 的 std140 规则在 C++ 侧写一份字段一一对应的镜像结构体，总大小对齐到 16 的倍数且 ≤ 256 字节（push constant）。
  3. 在 compile-shaders.ps1 注册源路径、模块名与 entry point，运行脚本产出三后端字节码 + 反射 JSON。
  4. 运行时用 ShaderReflectionCache::loadFromFile() 读反射，用 ShaderPipelineReflectionValidator::validate() 对齐管线布局，再交 RHI 创建 ShaderModule。
  5. 录制时用 pushConstants(stages, offset, sizeof(MyPush), &data) 推送；若尺寸/对齐不对，RHI 会在创建管线或录制期确定性报错。
