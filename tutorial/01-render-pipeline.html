01 渲染管线 Prototype Complete

arp 引擎的渲染管线是一条「后端中立」的链路：场景/UI 提取产出队列 → 渲染器声明 pass 并构建 DrawPlan → 帧图（FrameGraph）编译出确定执行计划 → RHI 后端录制原生命令。本文讲清楚这条链路上每个环节的职责与接口。

全景链路

1. RenderPipeline 接口

渲染管线的抽象基类 arp::renderer::RenderPipeline 定义了一帧的创建、缩放、渲染与构图契约。自定义管线通过 RenderFeature::registerPasses() 向 RenderPipelineBuilder 注册 pass。

class ARP_API RenderPipeline {
public:
  virtual const RenderPipelineDesc& desc() const = 0;
  virtual RendererResult create(const RenderPipelineCreateContext&) = 0;
  virtual RendererResult resize(rhi::Extent2D) = 0;
  virtual RendererResult render(RenderPipelineContext&) = 0;

  // 自定义管线实现：把 pass 录入帧图
  virtual RendererResult recordGraph(render_graph::RenderContext&,
                                RenderPipelineContext&);
  virtual RendererResult composeGraph(render_graph::FrameGraph&,
                                render_graph::TextureHandle backbuffer,
                                const RenderPipelineGraphCompositionContext&,
                                RenderPipelineFrameFeatures frameFeatures);
  virtual bool supportsGraphPostprocess(RenderGraphPostprocessPass) const;
};

用 RenderPipelineBuilder 声明 pass

pass 通过 addGraphicsPass() 声明其读/写纹理与执行回调，帧图据此推导依赖、生命周期与 barrier。

RenderPipelineBuilder builder(graph, backbuffer, desc);

builder.addGraphicsPass(
  "scene",
  /* reads  */ { { sceneDepth,  rhi::ResourceState::ShaderRead } },
  /* writes */ { { color,      rhi::ResourceState::ColorAttachment } },
  [](render_graph::RenderContext& rc,
     const RenderGraphColorTargetContext& ctx) {
     // 通过 RHI 编码器录制该 pass 的绘制命令
  });

2. FrameGraph：编译式帧执行计划

src/render_graph 负责帧级 pass 依赖、资源生命周期、barrier、瞬时别名、load/store 策略与队列/外部资源保护。你声明 pass 及其资源读写意图，FrameGraph 编译出一份确定的执行计划并驱动执行。

FrameGraph::addPass(name) 声明一个 pass，返回 PassBuilder；用 .read() / .write() / .writeAttachment() / .kind(PassKind) / .queue(QueueRole) 描述资源用途，最后 .execute(callback) 绑定录制回调（渲染器层 RenderPipelineBuilder::addGraphicsPass 只是它的薄封装，见 §1）。compile() 返回 CompiledFrameGraph，记录 pass、barrier、别名与生命周期计划；backend executor 仍要校验并消费相符的 lowering/payload，不能仅凭图已编译就视为可执行。

编译阶段产出
依赖 DAG由资源读写依赖生成 pass 执行顺序，检测依赖环
资源生命周期纹理/缓冲的首次/末次使用、生产者、消费者
Barrier 计划每个 pass 的 pre-pass barrier 批次，帧末恢复导入资源终态（如 swapchain → Present）
瞬时别名仅在 capability、资源生命周期/预算及 backend lowering 允许且有真实 allocation payload 时共享 GPU 内存；否则按 contract 禁止或失败
Load/Store附件 load/store、clear/dont-care、memoryless 策略
队列 & 外部资源graphics/compute/transfer/present 队列角色与导入资源保护
编译期校验读先于写、Load-on-Undefined、附件格式匹配、pass 种类一致性——不满足则确定性报错；无用 pass 经定点裁剪自动剔除

2.1 编译期保证

FrameGraph 的 compile() 阶段生成确定的资源与 pass 计划；执行阶段还要验证并消费目标 backend 的 lowering decision。计划与运行时 capability/payload 不一致时以诊断失败，不得静默改走其他路径。

  • Barrier 不在运行时二次推算：编译产出的 barrier 批次是唯一事实源，执行器逐 pass 回放。同一份图执行两次，输出一致。
  • 瞬时资源与 aliasing：FrameGraph 可生成生命周期与 alias 候选计划，但执行必须由与 capability 一致的版本化 lowering 决定。只有 contract 证明语义、预算和 completion/lifetime 均成立时才允许别名；没有等价 lowering 时必须关闭该能力或确定性失败，不自动替换成另一条成功路径。
  • 错误早发现：读未写入的资源、pass 种类与绑定的状态不匹配、附件格式不一致等问题在编译期即确定性报错，不会表现为运行时的静默错画或 UB。
  • 无用 pass 自动裁剪：输出未被任何后续 pass 消费的 pass（及其传递依赖链上的 pass）经定点迭代自动剔除。

2.2 子图（Subgraph）

FrameGraph 支持子图——把一组 pass 封装为可复用的单元，通过 typed pin 与父图连接。SubgraphRecipe 声明输入/输出 pin 的类型（颜色附件、深度附件、采样纹理、存储纹理/缓冲等），addSubgraph(recipe) 注册到帧图中，编译期完成局部编译后 link 进父图（句柄重映射、barrier 缝合）。子图可被整体裁剪（当所有输出 pin 均无消费者时）。

当前子图为 Prototype 级别：基本类型与最小验证已通过，完整集成仍在推进中。使用前请确认目标后端的支持情况。

FrameGraph::execute() 经 FrameGraphRhiActiveExecutor 执行编译后的图。保留 executionTrace()、resourceTrace()、passTrace()、attachmentTrace()、aliasTrace()、barrierTrace() 等诊断方法用于调试。

3. 渲染器：声明 pass + 构建 DrawPlan

渲染器（src/renderer）拥有场景、GUI、材质、光照、世界、后处理、调试等 pass 的声明与逐 pass 的绘制计划（DrawPlan）。DrawPlan 携带 submesh/材质的 push-constant 与 GUI 四边形/文本绘制命令顺序，经 RHI 命令编码器录制。

场景运行时可通过带 contract name/version 的 RenderFrameRequest payload 接入 renderer。payload 的生产者、消费者与版本必须匹配；示例集成不代表其他游戏或 backend 自动具有相同能力。

// 自定义管线 payload 契约（renderer/SceneRuntimePipelinePayload v1）
RenderFrameRequest req;
req.view    = { extent, colorFormat, frameIndex, deltaSeconds };
req.pipelinePayload = &payload;                 // SceneRuntimePipelinePayload
req.pipelinePayloadContractName = "arp::renderer::SceneRuntimePipelinePayload";
req.pipelinePayloadContractVersion = 1;

管线支持图形后处理 pass，目前内置 RenderGraphPostprocessPass::Fxaa。需由具体管线 supportsGraphPostprocess() 返回 true 并实现 recordGraphPostprocess()。

enum class RenderGraphPostprocessPass { Fxaa };

struct RenderGraphPostprocessContext {
  RenderGraphPostprocessPass pass = RenderGraphPostprocessPass::Fxaa;
  rhi::GpuTexture* sourceColor = nullptr;
  bool valid() const { return sourceColor != nullptr; }
};

5. RHI：设计哲学

src/rhi 不是又一个「包装 Vulkan」的图形抽象，而是一套有鲜明立场的引擎级 GPU API。理解它的设计哲学，才能正确使用其上的渲染管线、动画、粒子、UI 等系统。本节拆开讲清它的定位、分层、四条内部路径与硬约束。

5.1 定位：L2 是引擎面对的 GPU API

RHI 对外呈现的是 L2（Layer 2） 接口，它有三条设计基准：

  • WebGPU 式的对象安全与生命周期规则——资源有显式状态、句柄化、创建/销毁语义清晰，避免原生 API 的悬垂句柄陷阱。
  • Vulkan 级的显式渲染能力——push constant、次级命令缓冲、显式 barrier、队列族、显式内存控制等都作为一等公民暴露。
  • Descriptor-based 资源绑定——以描述符布局/集合/表为统一词汇，而非各家后端各自的绑定机制。

立场红线：RHI 不是 WebGPU 兼容层，也不被 WebGPU 特性集约束。WebGPU 只是其中一个后端目标（带内部翻译层），它不定义引擎 API 的上限。webgpu-research-decision.md 明确：即便有 WebGPU 后端，也不把引擎能力削平到 WebGPU 能表达的子集。

5.2 三层边界：L2 / semantics / backends

RHI 把「引擎概念」与「原生能力」严格分层，原生头永远不越过 L2 公共头：

  • L2 拥有引擎 GPU 对象、校验、描述符、命令录制、push constant、帧槽、可移植资源状态契约。
  • semantics 层拥有原生能力解释、后端分配意图、描述符翻译、管线编译策略、同步降级、表面获取/呈现语义。
  • backend 目录私有：src/rhi 包根的 L2 公共头保持无原生头；只有 backends/vulkan|metal|webgpu 内部的实现文件可 include 原生头，且不得把原生句柄暴露给 renderer/GUI/samples/FrameGraph/L2 公共头。
  • 原生优先（native-first）：semantics 层通过「能力 + 策略数据」暴露后端原生潜力（如 Vulkan 描述符索引、Metal 参数缓冲、WebGPU 浏览器限制），不把特性削平到最小公分母。

5.3 核心哲学：显式 lowering 结果

上层表达 L2 意图，不观察 native handle 或 backend-only 参数。每项可选能力都必须依据可追溯的 capability 和版本化 lowering contract，在执行前确定唯一结果：

路径含义对上层可见性
Native执行受 contract 约束的 native payload。由能力状态与诊断可观察
Equivalent / Emulated仅当 contract/test 证明保持 L2 语义时允许，例如受契约约束的 WebGPU push-constant upload-ring lowering。由能力状态与诊断可观察
Prototype / Legacy有版本、边界、预算且由调用方显式 opt-in；不得伪装为通用能力。必须显式可见
DiagnosticFailure能力、映射或语义无法证明时确定性拒绝。必须返回稳定诊断

硬约束：RHI、renderer、RenderGraph、UI、sample、game 与 asset pipeline 不得用 backend 局部修复绕过 L2 contract。CPU replay、degraded 状态或接口存在都不自动证明语义等价；不满足已声明 lowering 的路径必须失败关闭，或由显式、版本化 Prototype/Legacy opt-in 开启。

5.4 L2 决策链：从设备初始化到每帧编译

本节讲清 capability 与 lowering 决策何时产生、如何传递、在哪消费。Null、Vulkan、Metal、WebGPU 是共享 L2 必检 profile；WebGL1 的 ordered-graphics profile 单独 opt-in，不能继承这些 backend 的能力声明。

设备初始化（一次性）

backend 先从规范保证或 native runtime query 建立 capability contract，再按功能、格式与资源 ABI 生成并消费 lowering decision。聚合的 DeviceCapabilities 布尔值用于快速 gate；execution status、fallback plan 和实际 payload 也必须一致，不能只看布尔值宣称 backend 已验证。

NativeBackendCapabilityContract(backend)
  → chooseFeatureFallback(contract, feature)     → NATIVE / EMULATED / DEGRADED / FAIL
  → buildNativeEngineFallbackPlan(contract, requirements)
  → plan.applyTo(caps)
  → caps.features.*  (布尔能力门控，缓存到 DeviceCapabilities，每帧不重复)

能力布尔值只是必要的 fast gate，不足以证明实际执行路径。上层不得把 Degraded 当作等价成功；resource state、sync、lifetime、内存预算或可见结果可能变化时必须拒绝，除非调用方显式 opt-in 到版本化 Prototype/Legacy contract。

易错点：caps.features.* 不是 caps.memory.* 的别名；裸 native fact 不能替代 feature lowering。Metal transient aliasing 必须由真实 heap placement、预算、lifetime 和 completion probe/contract gate 决定，不能只凭 MTLHeap 存在推断可用。当前各 backend 结果以 能力矩阵为准。

每帧链路：L2 决策在编译期消费

Platform   acquireFrame() → renderGraphFrame() → presentFrame()

Renderer   RenderFrameDirector::compose()
              payload adapters → RenderFrameIntent → pass providers → FrameGraph passes
            ↓
            FrameGraph::compile()
              ① lowerSubpassGraph()     — 消费已验证的 subpass lowering decision
                 Native / Equivalent → 执行对应 contract payload
                 otherwise           → 确定性失败
              ② FrameGraphCompiler::compile()
                 validate → cull → resource lifetimes → barrier plan
                 → alias plan               — 读 caps.features.transientAliasing
                    Native   → 仅在预算、lifetime 与 backend contract 成立时计算 alias groups
                    otherwise → 不执行 aliasing 或确定性失败
            ↓
            CompiledFrameGraph
              pass order + barrier batches + aliasPlan + load/store
            ↓
            allocateTransientTextures(compiled)
              aliasPlan → backend-private allocation consumes validated lowering plan
              （allocation failure is diagnostic; no placeholder success）
            ↓
            FrameGraphExecutor::execute(compiled)
              replayPassBarriers() → beginRenderPass() → callbacks → queue->submit()

Backend    RHI 虚函数分发 → vulkan / webgpu / metal 命令录制
              （backend-private executor 验证并消费已选 lowering；不匹配则诊断失败）
L2 消费点输入允许结果
lowerSubpassGraphsubpass capability + versioned lowering decisionNative / Equivalent payload，或确定性诊断失败

FrameGraph 编译结果是执行计划，但 backend executor 仍必须验证并消费与之匹配的 capability/lowering decision。若运行时条件与计划不一致，必须以诊断失败，不能静默换路或返回占位资源。

5.5 后端中立的硬约束

架构边界是硬约束：renderer 与 render_graph 头文件不得 include Vulkan/Metal/WebGPU/Android/iOS 原生头；原生句柄不得上浮到 backend/platform 之上。

RHI 的迁移面（migration surface）是一组固定的公共头，新 renderer / RenderGraph 特性只能面向它们开发：

// RHI 迁移面（被移除的旧 src/rhi 不是生产兼容路径）
src/rhi/gpu_device.h
src/rhi/gpu_commands.h
src/rhi/gpu_resources.h
src/rhi/gpu_descriptors.h
src/rhi/gpu_pipeline.h
src/rhi/gpu_swapchain.h
src/rhi/gpu_frame_resources.h
src/rhi/pipeline_cache.h      // RenderPipeline/ComputePipeline/PipelineLayout 缓存
src/rhi/descriptor_cache.h    // DescriptorArena/DescriptorSet 跨帧缓存

RenderGraph 端新增的公开头（同样禁止暴露原生句柄）：frame_graph_resource_pool.h（瞬时纹理/缓冲跨帧池）、transient_resource_allocator.h（真实别名物理分配）、frame_graph_uniform_ring_buffer.h（每帧 uniform 环缓冲）。

5.6 关键模型要点

  • 描述符模型：公共词汇是 DescriptorLayout / DescriptorSet / DescriptorTable / DescriptorArena / PipelineLayout / PushConstantRange。WebGPU 的 bind group、Metal 的 argument binding、Vulkan 的 descriptor set 都只是后端的映射目标。DescriptorArena 容量受限，分配失败确定性返回诊断而非热路径中静默扩容；reset() 开启新分配代（generation），旧代分配出的 set/table 变为 stale 并拒绝再写入/绑定。
  • 可变帧槽（≥2）：契约使用至少两个逻辑帧槽，请求图像数量由帧槽数决定（要求 >= 2，默认仍 2 以向后兼容）；即便平台需要更多原生缓冲，L2 依旧只暴露约定的帧在途，并针对原生差异报诊断。帧局部的描述符 arena、上传环、命令池、延迟销毁、瞬时资源都按帧序号取模帧槽数索引。
  • 命令模型：以 CommandEncoder 与类型化 pass encoder 录制。secondary command、render bundle 与 CPU replay 是否可用取决于显式 lowering；CPU replay 不能证明 native GPU 语义。Null 是 reference validator，不是 GPU 执行证据。
  • 同步与帧资源生命周期：Fence、semaphore、timeline 与 completion 只有真实满足 completion/order/lifetime 语义时才可声明可用。Vulkan、Metal、WebGPU 的公开工厂和 queue-private sync 有不同边界；WebGPU callback 仅用于 backend-owned retirement，不等于 L2 timeline。WebGL1 的 flush/present 也不构成 GPU completion。请以能力矩阵为准，不依赖固定的 N+2 帧延迟或 host no-op wait 来推断安全回收。
  • PSO / 描述符缓存（热路径零重建）：L2 提供 PipelineCache 与 DescriptorCache。管线与描述符集合按稳定 key（stableRenderPipelineStateKey / stableComputePipelineStateKey / stablePipelineLayoutKey 及描述符布局 hash）缓存，device.pipelineCache().acquireRenderPipeline(...) 仅在 miss 时创建、命中即复用，并按帧 onFrameComplete() + fence-gated 淘汰陈旧项。每 pass 每帧的 pipeline/描述符/纹理重建被消除。
  • 统一 uniform 环缓冲：FrameGraphUniformRingBuffer 为每个帧槽预分配 backing buffer，并按 256 字节对齐进行有界 bump allocation。游标只能由带原始 completion issuer 的 resetOrdered() 凭证回收；旧的 onFrameComplete() 不构成 GPU completion 证明，会确定性拒绝。
  • push-constant 硬上限：RHI 在帧计划阶段由 validatePushConstants 为 pushConstantSizeBytes > 256 产生确定性诊断，执行计划不准提交；目标 backend 还需通过自己的能力与 payload gate。
  • 别名内存：Transient aliasing 由共享 L2 contract、lifetime/size/peak-budget 验证、真实 completion 与 backend allocation payload 共同决定。失败时不得返回 size-only heap 或 placeholder texture。Vulkan、Metal、WebGPU 与 WebGL1 的当前结论见能力矩阵。

5.7 公共对象模型（引擎侧 API）

上层代码只通过这些虚拟接口操作 GPU 对象，拿到的全是引擎句柄，从不见 Vk*/id<MTL...>/WGPU*：

class ARP_API GpuDevice {
public:
  Backend backend() const;
  DeviceCapabilities capabilities() const;
  MemoryStats memoryStats() const;

  GpuQueue& queue();
  QueueSubmitResult submit(const CommandBuffer&);
  QueueSubmitResult submit(const CommandBuffer&, GpuFence* signalFence);          // fence-gated 回收
  QueueSubmitResult submit(const CommandBuffer&, GpuTimelineSemaphore* sem, std::uint64_t value);

  GpuFence*            createFence();             // signal / wait / reset（L2 语义，无原生句柄）
  GpuSemaphore*        createSemaphore();
  GpuTimelineSemaphore* createTimelineSemaphore();

  PipelineCache&   pipelineCache();    // 跨帧缓存 RenderPipeline/ComputePipeline/PipelineLayout
  DescriptorCache& descriptorCache();  // 跨帧缓存 DescriptorArena/DescriptorSet

  GpuBuffer*     createBuffer(const BufferDesc&);
  GpuTexture*    createTexture(const TextureDesc&);   // TextureDesc 现含 sampleCount
  GpuSampler*    createSampler(const SamplerDesc&);
  PipelineLayout*       createPipelineLayout(const PipelineLayoutDesc&);
  RenderPipeline*      createRenderPipeline(const RenderPipelineDesc&);
  ComputePipeline*     createComputePipeline(const ComputePipelineDesc&);
  DescriptorArena*     createDescriptorArena(const DescriptorArenaDesc&);
  CommandEncoder*      createCommandEncoder(const CommandEncoderDesc&);
  Swapchain*           createSwapchain(const SwapchainDesc&);
};

热路径上的管线与描述符走缓存而非即时创建；提交可携带 fence 以便帧资源在信号后回收：

// PSO 缓存命中即复用，仅在 miss 时创建
RenderPipeline* pipe = device.pipelineCache().acquireRenderPipeline(desc);   // 不重复创建

// 提交时挂 fence，帧末信号后回收该帧的瞬时/延迟资源
GpuFence* fence = device.createFence();
device.queue().submit(*cb, fence);

录制一段绘制的最小闭环也完全在引擎类型内：

// 命令编码器 → 类型化 pass 编码器，全程无原生 API
CommandEncoder* enc = device.createCommandEncoder({ "frame" });
RenderPassEncoder* pass = enc->beginRenderPass(renderPassDesc);
pass->setPipeline(*pipeline);
pass->bindDescriptorSet(0, *dset);
pass->pushConstants(ShaderStage::Vertex, 0, sizeof(mvp), &mvp);
pass->drawIndexed(indexCount, 1, 0, 0, 0);
CommandValidationResult r = pass->end();
CommandBuffer* cb = enc->finish();
device.queue().submit(*cb);

5.8 状态分级约定

RHI（及整个引擎文档）用一套统一的状态标签标注成熟度。读文档时务必区分，它们之间有不可逾越的阶梯：

状态含义门槛
Contract Complete公开/语义契约已定义并被确定性测试覆盖—
Prototype Complete在显式 gate/有限范围内有可用实现与冒烟覆盖非生产默认
Backend Validated指定平台上通过后端的冒烟/契约矩阵需命名后端证据
Platform Validated浏览器/移动/桌面/生命周期行为通过平台级验证需命名目标证据
Production Ready既定生产路径，旧回退退役，全回归/冒烟矩阵有当前证据需 backend+platform+migration+telemetry+lifetime+smoke 全部证据

阶梯不可跳：Contract Complete、Prototype Complete、Backend Validated、Platform Validated 与 Production Ready 表示不同证据等级。能力按 feature/backend/platform 分别评估；请查看当前 RHI Capability Matrix 和 Platform Build Matrix，不要沿用本教程旧的整体 readiness 或待验证清单。

6. Shader

着色器子系统（Slang 统一着色语言、多后端编译、反射缓存与 Pipeline 校验、以及统一内存对齐约定）已从渲染管线独立成章，详见 09 Shader。它与本页 §5 的 RHI 共享同一条设计哲学：上层写一次，后端分支在底层完成——你只面对 Slang 与反射元数据，不接触任何原生着色器方言。

想了解 arp 的shader ABI 与矩阵布局（CPU 镜像、反射/contract test、256 字节 L2 push-constant 上限），直接读 第 09 章。

示例与当前能力边界

仓库示例覆盖不同的集成路径，并非同一个通用渲染能力样板。Windows/Vulkan 游戏示例与 Build a Queen 的 WebGL1 ordered-graphics Prototype 有不同的资源、执行与验证契约；在评估功能或扩展 renderer 前，先确认目标 backend 的 能力单元格及其证据。

快速上手清单

  1. 实现 RenderPipeline（或复用内置场景运行时管线），用 RenderPipelineBuilder::addGraphicsPass() 声明每个 pass 的读写纹理与回调。
  2. 在回调内通过 RHI 命令编码器录制绘制（使用渲染器提供的 DrawPlan，而非自行遍历 submesh）。
  3. 需要后处理时，让 supportsGraphPostprocess() 返回支持项并实现 recordGraphPostprocess()。
  4. 把帧请求包成 RenderFrameRequest（含 payload 契约名与版本），交给 RenderSystem 执行。
  5. 保持后端中立：只在 rhi/backends 与 platform 内写原生代码。
