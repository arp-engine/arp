08 网络系统（network）

arp 的网络层（src/network/）是一套 asio 风格的跨平台 I/O 抽象：事件循环 io_service 驱动每个对象的 io_context，在其上叠 tcp/udp socket，再往上提供 HTTP、WebSocket、TLS 客户端。它把「传输细节」做成类型安全的 ClientTransportKind 决策，便于后端中立与确定性诊断。

状态：Stable io_service / socket / tcp / udp / http::Client / websocket::Client / tls 均已实现可用。文档中反复提到的更高层门面 NetworkService / NetworkStream / CompletionQueue 目前属于契约 / 迁移目标（源码 src/network 中尚未落地），本页以已实现的 API 为主线。

8.1 分层模型

8.2 事件循环：io_service 与 io_context

io_service 是真正的事件循环，内部有 worker 线程 + poller，调用 run() 会阻塞驱动 I/O；io_context 是绑定到具体 socket / 客户端的每对象上下文——它既可以被某个 io_service 驱动，也可以独立构造（此时自己持有一个 io_service，见 owned_service_）。

#include "network/io_service.h"
#include "network/io_context.h"
#include "network/http/client.h"
using namespace arp::network;

// 方案 A：独立 io_context（自带 io_service）
io_context ctx;                          // 内部拥有 io_service
http::Client client(&ctx);

// 方案 B：显式事件循环 + 绑定 ctx
io_service svc;
io_context ctx2(&svc);                   // ctx2 由 svc 驱动
http::Client client2(&ctx2);

// 在专用线程上跑事件循环
std::thread loop([&svc]() { svc.run(); });   // 阻塞；用 svc.wakeup()/close() 退出
// ... 发出异步请求 ...
svc.close();
loop.join();

io_service 关键方法：run() / wakeup() / close() / schedule(timer) / execute(op) / time() / quit()。io_context 关键方法：dispatch() / post_complete(cb) / run_at / run_after / run_every / now() / start_op(op) / service()。

8.3 寻址：endpoint

endpoint 封装 sockaddr_storage（IPv4 / IPv6 透明）：

using namespace arp::network;

endpoint ep("127.0.0.1", 8080);          // 字符串 IP + 端口
if (!ep.is_valid()) { /* ... */ }

endpoint server = endpoint::anyaddr<ipv4>(9000);   // 监听 0.0.0.0:9000
endpoint loop   = endpoint::localhost<ipv4>(9000);  // 127.0.0.1:9000

core::pmr::Vector<endpoint> resolved;
error_code ec;
endpoint::resolve(ec, "example.com", "443", AF_UNSPEC, SOCK_STREAM, 0, resolved);
bool v6 = ep.is_ipv6();
core::pmr::String text = ep.to_string(); // "127.0.0.1:8080"

8.4 TCP socket

tcp::socket<ipv4> 是 stream_socket 的别名。支持同步与异步两种范式：

方法说明
open(ec) / bind(ec, ep) / listen(ec, backlog)建立监听
accept(ec, sock)接受连接（注意：源码里另有一个拼写 accecpt 的别名，统一用 accept）
connect(ec, ep)发起连接
send(ec, buf, size) / recv(ec, buf, size) / recvall(ec, buf)同步收发
async_connect(ep, h) / async_send(buf, h) / async_recv(buf, h) / async_accept(sock, h)异步收发（回调 handler）
set_nodelay / set_reuseaddr / set_keepalive / set_nonblockingsocket 选项
set_sni(host) / set_socks5_proxy(ep)TLS SNI / SOCKS5 代理

服务端 / 客户端最小示例：

// 服务端（在 io_context ctx 驱动下）
tcp::socket<ipv4> listener(&ctx);
error_code ec;
listener.open(ec);
listener.set_reuseaddr(ec, true);
listener.bind(ec, endpoint::anyaddr<ipv4>(9000));
listener.listen(ec, 8);
tcp::socket<ipv4> peer(&ctx);
listener.accept(ec, peer);               // 阻塞等待一个连接
byte_buffer buf { &core::defaultCpuMemoryResource() };
peer.recvall(ec, buf);                    // 收满 buf 再返回
peer.send(ec, buf.data(), buf.size());   // 回显

// 客户端
tcp::socket<ipv4> sock(&ctx);
sock.open(ec);
sock.connect(ec, endpoint("127.0.0.1", 9000));
sock.send(ec, "ping", 4);
byte_buffer in { &core::defaultCpuMemoryResource() };
in.resize(4);
sock.recvall(ec, in);

8.5 UDP socket

udp::socket<ipv4> 是 datagram_socket 的别名，面向无连接数据报：

udp::socket<ipv4> s(&ctx);
error_code ec; s.open(ec);
endpoint dst("127.0.0.1", 9000);
s.sendto(ec, dst, "hello", 5);

endpoint from;
byte_buffer pkt { &core::defaultCpuMemoryResource() };
pkt.resize(512);
socklen_t n = s.recvfrom(ec, from, pkt);  // 收到 pkt.size() 字节或错误

8.6 HTTP 客户端

http::Client 把「请求对象」与「事件回调」解耦：先构建 ClientRequest（get/post），再交给 async_send / async_stream。是否走 TLS 由 URI scheme 决定。

#include "network/http/client.h"
using namespace arp::network::http;

Client client(&ctx);

ClientRequest req = ClientRequest::get("https://api.example.com/v1/status");
req.add_header("Accept", "application/json");
req.set_content_type(ContentType::json);

client.async_send(req, [](const ClientStatus& status, const Response& resp) {
    if (!status.success()) {
        // status.transport_error / status.diagnostic / status.tls_diagnostic
        return;
    }
    // resp 已解析：headers + body
});

// 流式（大响应 / SSE）：分 on_headers / on_body / on_complete 三段回调
client.async_stream(req,
    [](const Response& headers) { /* 首字节头 */ },
    [](StringView chunk)        { /* 每个 body 分片 */ },
    [](const ClientStatus& st)  { /* 完成 */ });

传输决策来自 Client::prepareTransport(uri)，返回 ClientTransportKind：

枚举值含义
http_cleartexthttp:// 明文
websocket_cleartext该 URI 其实是 WS（HTTP 客户端会拒绝）
tls_requiredhttps:// 需要 TLS；若 TLS 后端未启用则报 tls_unavailable

8.7 WebSocket 客户端

websocket::Client 用于长连接双向通信（如实时对战 / 热更新推送）：

#include "network/websocket/client.h"
using namespace arp::network::websocket;

Client ws(&ctx);
auto req = ClientRequest::connect("ws://127.0.0.1:9000/live");

ws.async_connect(req, [](const ClientStatus& st) {
    if (!st.success()) return;
    // 连上后发送文本帧
    ws.send_text("hello", [](const ClientStatus& s) { /* 发送完成 */ });
    // 持续读帧
    ws.async_read_frame([](const ClientStatus& s, const Frame& frame) {
        if (!s.success()) return;
        // frame.payload() / frame.is_text() ...
    });
});

// 关闭
ws.async_close(1000, "bye", [](const ClientStatus& s) { /* 关闭完成 */ });

注意：send 与 send_text 都是对 async_write_text 的封装；二进制走 async_write_binary(byte_buffer)。写/读/关都要求当前处于 ActiveTransport::direct 且 stream_ 已建立，否则回调直接拿到 connection_closed。

8.8 TLS

加密由 tls:: 命名空间提供：TlsContext / SslStream / TlsConfig / TlsStatus / TlsDiagnosticCode。HTTP/WS 客户端在 https:// / wss:// 时自动走 TLS 握手；可在 ClientRequest::tls_config() 上定制证书 / SNI 等。

TLS 后端是编译期开关：仅当定义 ARP_NETWORK_TLS_BACKEND_OPENSSL 时 wss:// 才能握手成功；否则 async_connect 立即以 tls_diagnostic == disabled / http_diagnostic == tls_unavailable 失败（见 websocket::Client::async_connect）。这一点对「后端中立」契约至关重要——所有诊断都通过 ClientStatus / TlsDiagnosticCode 返回，而非抛异常。

8.9 后端中立与确定性诊断

网络层遵循 network-typed-transport-governance.md 的「类型化传输」治理：

  • 传输决策集中：一切以 ClientTransportKind 为先，禁止在业务层散落 if (https) 分支。
  • 诊断结构化：失败统一返回 ClientStatus（含 transport_error / diagnostic / tls_diagnostic），可据此稳定判断原因、写日志、做重试策略。
  • 确定性：诊断枚举值与顺序固定，便于第 06 章资源系统那样做遥测与指纹比对。
  • 无异常跨 ABI：所有错误走 error_code + 诊断码，不穿过 ARP_API 边界抛 C++ 异常。
迁移提示：文档中的 NetworkService / NetworkStream / CompletionQueue 是更高层、面向「游戏会话」的门面（意图把 io_service/socket/http/ws 统一封装）。在源码落地之前，请直接基于本页的 io_service + io_context + 各客户端 API 开发；待门面就绪可平滑替换上层调用。

8.10 参考实例：与资源遥测的衔接

回到 games/world_of_claudecraft 的视角：若要让客户端拉取热更新内容或上报资源遥测（见第 06 章 ResourceReloadTelemetry），可用 http::Client 在 app 启动时绑定到引擎的 io_context：

// 概念示例：在引擎的 io_context 上用一个 HTTP 客户端拉取配置
arp::network::io_context& appCtx = engine.ioContext();   // 由引擎 bootstrap 提供
arp::network::http::Client liveClient(&appCtx);

auto cfgReq = arp::network::http::ClientRequest::get("https://cdn.example.com/wocc/live.yaml");
liveClient.async_send(cfgReq, [](const arp::network::http::ClientStatus& st,
                                 const arp::network::http::Response& resp) {
    if (st.success()) {
        // 把 resp.body 交给第 06 章的反序列化 / 第 07 章的 deserialize_from_yaml
    }
});

这里 engine.ioContext() 仅为示意入口——确切的获取方式取决于引擎 app 引导如何暴露 io_context；重点是三套系统如何串起来：网络取字节 → 反射/资源反序列化 → 运行时对象。
